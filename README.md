# АРМ Теплооблік — веб-додаток

Застосунок для зняття та аналізу показань **приладів комерційного обліку
теплової енергії** (обчислювач + витратомір + ТСП) — бригадний збір у полі,
аналітика Гкал і друк актів. Заміна Excel-книги ЗБЛ: введення показань,
підрахунок спожитих Гкал, питоме споживання, імпорт реальної книги `.xlsm`.

> **Клас приладу.** Комерційний — той, за яким виставляються рахунки (на вводі
> в будинок); розподільчий — сублічильник усередині будинку. Клас береться з
> колонки «Комерційний облік» книги; аналітика рахує **за комерційними**.
>
> **Одиниці.** Обчислювачі бувають у Гкал, МВт, ГДж, кВт — обсяг приводиться до
> **Гкал** (коефіцієнти у `Component.UNITS`). Питоме споживання — Гкал на
> одиницю розрахункового теплового навантаження (з таблиці TabTN книги): саме
> воно дозволяє порівнювати будинки різного розміру між собою.

## Запуск

Потрібен звичайний HTTP-сервер (через `file://` модулі можуть не завантажитись):

```bash
python3 -m http.server 8000
# відкрийте http://localhost:8000/
```

Будь-який статичний сервер підійде (`npx serve`, `php -S`, nginx). Для GitHub
Pages — Source: Deploy from a branch, тека `/ (root)` (файл `.nojekyll` вимикає
Jekyll, щоб `vendor/` віддавалась без змін).

## Власний сервер бригадного збору (`server.js`)

Для роботи командою (старший + кілька робітників) у локальній мережі —
запустіть вбудований сервер (Node.js, **без залежностей**):

```bash
node server.js            # порт 8083 за замовчуванням
PORT=8083 node server.js  # явно
```

Він **і роздає додаток, і зберігає спільні дані**. Пристрої на тому ж Wi-Fi
відкривають `http://<IP-сервера>:8083/` (напр. `http://192.168.1.47:8083/`).

**Авторизація**: при першому запуску створюється **адміністратор (старший)**;
далі він у розділі «Користувачі» додає робітників (ім'я + PIN). Кожен входить
під своїм ім'ям і PIN — воно й підписує показання; **адмін = Старший**,
звичайний користувач = **Робітник**. Список користувачів спільний (на сервері),
PIN перевіряється на пристрої (тож вхід працює й офлайн з кешу).

Робочий цикл (усе працює **офлайн-перше** — лічильники в підвалах без зв'язку):

1. **Старший**: імпортує книгу ЗБЛ → у панелі «Виконавець» → «Опублікувати базу
   на сервер». Розподіляє котельні між робітниками (вибір робітника зі
   **списку**); для великих котелень — «по будинках», щоб віддати окремі
   будинки різним робітникам. «Зберегти завдання на сервер» — і воно
   доходить робітникам автоматично. Робітник бачить своє через «Тільки мої»,
   а решту будинків (поза завданням) може переглядати й знімати, вимкнувши
   фільтр або через пошук у «Вводі».
2. **Робітник**: відкриває адресу сервера, входить → «Завантажити базу з сервера»
   (файл не потрібен) → за потреби «Завантажити завдання з сервера» (підтягує
   лише розподіл, **не чіпаючи** локальну чергу показань) → знімає показання
   **офлайн** (зберігаються локально, у черзі).
3. **Автосинхронізація**: щойно з'являється мережа, черга **сама** йде на сервер,
   а дашборд старшого (прогрес по котельнях/робітниках) **оновлюється наживо**.
   Синхронізацію можна вимкнути або запустити вручну кнопкою.

**Захист від втрати даних.** «Завантажити базу з сервера» та імпорт книги
повністю замінюють локальну базу — якщо є **незвигружені** показання, застосунок
попередить і вимагатиме явного підтвердження (спочатку синхронізуйте!).
Помилково збережене **польове** показання можна видалити прямо в архіві «Вводу»
(✕ на рядку; записи з книги недоторканні; робітник видаляє лише свої). Після
збереження тост пропонує «**Наступний ›**» прилад будинку, а успішні
повідомлення зникають самі.

**Розмежування прав у полі.** Паспортні дані приладів (заводські номери,
повірки, тип, розмірність, теплове навантаження, частка, ком. облік/ФОП) та
**попередні** показники веде **старший** — у робітника ці поля лише для
читання. Робітник у довіднику редагує й зберігає **тільки** «Контактну інфо.»
та «Телефон», а в показаннях вводить **поточні** значення (попередні беруться
з бази й не змінюються). Так дані приладів не розходяться між пристроями.

Дані сервера — у `arm-data/db.json` (у `.gitignore`, тож персональні дані **не**
потрапляють у репозиторій). Без сервера додаток працює як і раніше та має
резервний **обмін файлами** (`.json`) через месенджер.

### Розгортання на Apache (без Node) — `api.php`

Якщо сайт уже роздає **Apache** (напр. `http://195.64.183.13:8083/`), окремий
Node-процес запускати не треба — той самий API дає **`api.php`** (PHP-версія
`server.js`, ті самі маршрути й формат). Кроки:

```bash
sudo apt install php libapache2-mod-php   # якщо PHP ще немає
# покласти api.php і .htaccess у теку сайту (там же index.html, support.js, vendor/)
sudo mkdir -p /var/www/арм/arm-data
sudo chown www-data:www-data /var/www/арм/arm-data   # веб-серверу потрібен запис
sudo a2enmod rewrite && sudo systemctl restart apache2   # для красивих URL /api/…
```

Клієнт **сам визначає**, який шлях доступний: `/api/…` (Node або Apache з
`mod_rewrite`) чи `/api.php/…` (Apache без переписування URL — працює завжди).
Тож `.htaccess`/`mod_rewrite` необов'язкові — достатньо покласти `api.php`.

> 🔒 **Захист теки даних не залежить від `mod_rewrite`.** Оскільки він
> необов'язковий, `arm-data/` закрито трьома незалежними шарами: правило
> `mod_rewrite`, правило `mod_alias` (`RedirectMatch 403`) і заборона за іменем
> файлу через `mod_authz_core` — плюс окремий `arm-data/.htaccess`
> (`Require all denied`), який **сервер створює сам** при першому записі.
> Якщо теку робите руками (як у командах вище) — захист доїде з першим
> збереженням; перевірити можна так:
>
> ```bash
> curl -s -o /dev/null -w '%{http_code}\n' http://ВАШ-СЕРВЕР/arm-data/db.json
> # має бути 403 (або 404), але НЕ 200
> ```

> Фото передаються як data URL у складі показань. Щоб великі пакети не
> обрізались, у `php.ini` бажано `post_max_size = 64M` (і `upload_max_filesize`).

### OCR-контроль показань з фото (звірка старшим)

Старший (онлайн, в офісі) може **звірити введений показник із розпізнаним на
фото**: у деталі приладу («Ввід» → архів) поряд із фото зʼявляється кнопка
**«🔎 Звірити з фото»**. Сервер надсилає фото до хмарної vision-моделі
(Anthropic Claude), розпізнає число й порівнює з введеним: збіг підсвічується
🟢 зеленим, розбіжність — 🔴 червоним («на фото X, введено Y»). Робітник у полі
й далі вводить показник вручну — фото лишається контролем, а розпізнавання йде
на сервері (ключ API нікуди не потрапляє на пристрій).

**Налаштування** — у файл `arm-data/config.json` (поряд із базою; **не** у
репозиторії — вся тека `arm-data/`, разом із бекапами й фото, закрита від
прямого доступу через веб, див. врізку вище):

```json
{
  "anthropicKey": "sk-ant-...",
  "ocrModel": "claude-opus-4-8"
}
```

- Ключ можна задати й через змінну середовища `ARM_ANTHROPIC_KEY`.
- `ocrModel` необовʼязковий (типово `claude-opus-4-8`). Для здешевлення при
  великому обсязі фото можна вказати легшу vision-модель, напр.
  `"claude-haiku-4-5"` чи `"claude-sonnet-5"`.
- Потрібен вихід в інтернет із сервера й **PHP cURL** (для Apache) — зазвичай
  уже встановлено. Кнопка звірки зʼявляється лише коли ключ налаштовано.
- Кожна звірка — один платний запит до моделі; запускається вручну старшим по
  конкретному показанню, тож витрати контрольовані.

### Встановлення як застосунок (PWA) + офлайн-оболонка

Додаток містить `manifest.webmanifest` та service worker (`sw.js`), які:
- **кешують оболонку** (`index.html`, `support.js`, `vendor/`, іконки) — застосунок
  **відкривається офлайн**, навіть якщо вкладку закрили в підвалі без зв'язку;
- дають змогу **«встановити» застосунок** на домашній екран (іконка, повноекранний
  режим, без адресного рядка);
- **ніколи не кешують `/api/…`** — дані завжди свіжі, синхронізація чесна.

Коли браузер визнає застосунок встановлюваним, згори зʼявляється власний банер
**«Встановити застосунок»** з кнопкою (перехоплюємо подію `beforeinstallprompt`,
бо Chrome більше не показує банер сам); на iOS Safari — підказка «Поділитися →
На екран «Домашній»». Банер можна приховати (✕) — більше не турбує. Умова та сама,
що й для офлайн-режиму: **HTTPS із довіреним сертифікатом** (див. нижче).

> ⚠️ **Потрібен HTTPS із ДОВІРЕНИМ сертифікатом.** Браузери реєструють service
> worker лише на `https://` або `http://localhost`. На `http://` з IP-адресою
> (напр. `http://195.64.183.13`) SW **не активується**.
>
> **Важливо:** самопідписаний сертифікат, який браузер вважає ненадійним
> («Ненадійно»/⚠ в адресному рядку), Chrome **все одно блокує** — реєстрація
> service worker падає з SSL-помилкою, і офлайн-режим не працює, навіть якщо
> ви натиснули «Все одно продовжити». Сертифікат має бути **довіреним**:
> - **Let's Encrypt** (безкоштовно), якщо є доменне ім'я:
>   `sudo apt install certbot python3-certbot-apache && sudo certbot --apache`;
> - **mkcert** для локальної мережі: `mkcert` генерує локальний кореневий CA;
>   встановіть цей **root CA на кожен телефон** (Android: Налаштування → Безпека
>   → Шифрування й облікові дані → Встановити сертифікат → Сертифікат CA), і
>   самопідписаний сертифікат стане довіреним → з'явиться 🔒 → SW запрацює.
>
> Стан офлайн-режиму видно **в самому застосунку**: «Виконавець» → картка
> «Офлайн-режим готовий ✓» (зелена) або пояснення причини (сертифікат / http).

## Можливості

- **Огляд** — помісячно (селектор звітних періодів): спожито ТЕ за різницею
  показань приладів, закриття місяця (скільки комерційних приладів подали
  показання), динаміка споживання за періодами, порівняння сезон-до-сезону,
  топ споживання, **повірка приладів** (прострочені / найближчі 90 днів) та
  **експорт місячного звіту в CSV**. Обсяг будинку = сума **комерційних**
  приладів обліку; розподільчі (поквартирні) — частка всередині будинку й у
  загальний обсяг не входять.
- **Будинки** — список **згрупований за будинком (адресою)** з лічильником
  приладів обліку; пошук (адреса, № приладу, **особовий**, власник, населений
  пункт, **телефон** — телефон/особовий шукаються й без урахування пробілів і
  формату), фільтр за котельнею, фільтри **«Тільки мої»** (моє завдання) та
  **«Незняті»** (лише будинки, де збір ще не завершено — зведення при цьому
  рахується по повному обсягу), сортування, експорт CSV. Робітник бачить свій
  **денний підсумок** («Сьогодні ви зняли N приладів»). Клік по будинку
  відкриває **деталь будинку зі списком приладів обліку/абонентів** (№ О/Р,
  обчислювач, факт / ТН, відхилення).
- **Аналітика** — за обраний місяць, із перемикачем метрики:
  - **Обсяг, Гкал** — споживання по котельнях (частка кожної) із переходом до
    будинків; у деталізації — відхилення факту від нормативу по будинку (там,
    де в книзі є навантаження, тривалість і t сер.).
  - **Питоме, Гкал/ТН** — питоме споживання на одиницю теплового навантаження:
    рейтинг котелень і будинків за інтенсивністю (лише де в книзі є ТН).
- **Ввід** — форма введення показань. Угорі — **велике поле «Новий показник»**
  (одна цифра, щоб швидко вносити в підвалі) з живим підрахунком спожитих Гкал і
  валідацією (поточний ≥ попереднього). Нижче — **«🌡 Повні показники приладу»**,
  що розгортається за потреби:
  - таблиця *Попередній / Поточний / Різниця* — **Кількість ТЕ**, **Обʼєм води**,
    **Наробіток**, **Простій**;
  - миттєві параметри — **витрати теплоносія**, **миттєва потужність**,
    **температура вхід/вихід**;
  - **показники водоміра** окремою таблицею + **відхилення використання**
    (лічильник проти водоміра; норма ±3 %, більше — підсвічується);
  - **оцінка споживання** — тривалість, t середньодобова, t приміщення,
    **Q факт.**, **норматив Q розр.**, різниця й відхилення у %.

  Можна додати **кілька фото приладу** (камера або галерея) — вони зменшуються,
  зберігаються разом із показанням і доступні в архіві та картці будинку.
  У картці абонента ведеться **паспорт вузла обліку**: обчислювач (повірка, тип,
  розмірність), витратомір (завод. №, повірка, тип, DN), ТСП (завод. №, повірка),
  теплове навантаження будинку, частка абонента (з автопідрахунком
  розрахункового ТН), позначки «Ком. облік» і «ФОП».
- **Картка будинку** — архів показань, навігація «← Попер. / Наступн. →»,
  кнопка додати показання.
- **Імпорт** (іконка бази у шапці) — приймає `.xlsm` / `.xlsx`:
  - `Довідники!TabAbon` → будинки/абоненти;
  - `Довідники` (TabTN) → теплове навантаження (за адресою);
  - `Архів!TabBaza` → історія показань (з'єднання за адресою будинку).
- **Бригадний збір** (роль виконавця у шапці) — «Старший» / «Робітник» + ім'я.
  Кожне зняте показання підписується ким/коли знято. У списку «Будинки» —
  **статус збору** кольором: 🟢 знято (всі прилади) · 🟡 частково · ⚪ чекає,
  зі зведенням «Зібрано N / M» та прогресом.
- **Обмін файлами (без сервера)** — у панелі «Виконавець»:
  - Старший розподіляє котельні між робітниками і **експортує завдання**
    (`.json`); робітники його імпортують і бачать «Тільки мої».
  - Робітник **вигружає пакет за день** (`.json` з показаннями + фото) і надсилає
    старшому в месенджер.
  - Старший **імпортує пакети** (той самий значок бази приймає і `.xlsx`, і
    `.json`) — показання **ідемпотентно зливаються** у майстер-базу
    (дедуплікація за особовим+датою, перемагає пізніше зняте, лічильник
    конфліктів, перевірка підпису бази).
  - **Дашборд старшого** (у «Будинки» → «Хто зібрав / що лишилось»): прогрес
    збору **по котельнях** (з призначеним робітником) і **по робітниках**
    (скільки приладів здано / залишилось).
- **Теми** (світла/темна) і **розмір шрифту** — у шапці.
- **Збереження** — база та введені показання зберігаються в **IndexedDB** і
  відновлюються при наступному відкритті.
- Кнопка **«Демо-дані»** на порожньому екрані — для швидкого ознайомлення.

## Розрахунок (порт із VBA книги ЗБЛ)

```
Обсяг ТЕ, Гкал = приріст × коеф_одиниці   (МВт 0.86 / ГДж 0.2388 / кВт 0.00086 / Гкал 1)
Q розрахункове = (ТН / 1000) × тривалість × частка × (18 − t_сер) / 41
Різниця = факт − норматив;   % = Різниця / норматив × 100
```

При імпорті авторитетними є збережені у книзі значення Q; де порожньо — факт
(Гкал) до-обчислюється з приросту показань.

| `index.html` | Сам додаток (шаблон `x-dc` + клас логіки `Component`) |
| `support.js` | Рантайм document-component (рендерить шаблон через React) |
| `vendor/react*.js` | React 18.3.1 (UMD), локально — без зовнішнього CDN |
| `vendor/xlsx.full.min.js` | SheetJS — розбір `.xlsx` / `.xlsm` |
| `server.js` / `api.php` | Бекенд бригадного збору: Node або PHP, ті самі маршрути |
| `sw.js` | Service worker — офлайн-оболонка й встановлюваність |
| `tests/` | Перевірки, що ганяються в CI на кожен пуш (див. нижче) |

## Перевірки (CI)

`index.html` — моноліт: шаблон і клас логіки в одному файлі, а зв'язок між ними
рядковий. Тому в CI (`.github/workflows/ci.yml`) на кожен пуш ганяються:

```bash
node --check server.js && node --check sw.js   # синтаксис бекенда й SW
node --test tests/*.test.js                    # merge-логіка сервера
node tests/check-app.js                        # статика index.html
node tests/render-check.js                     # рендер у справжньому браузері
php -l api.php                                 # лінт PHP-бекенда
```

**Рендер-тест** (`tests/render-check.js`) закриває пролом, якого не бачить
жодна статична перевірка: якщо `{{ ov.якийсь }}` у шаблоні не має відповідного
ключа в `renderVals`, рантайм **не падає** — він малює порожнє місце й лише
пише в консоль. Тест бутить застосунок у headless-Chromium із демо-даними,
обходить усі вкладки на телефонній і ПК-верстці й падає при JS-помилці,
невирішеному плейсхолдері або маркерах помилок рантайму в DOM. Тест
герметичний: зовнішні запити глушаться, сервера бригади навмисно немає —
перевіряється саме офлайн-режим.

Локально потрібен Playwright (у репозиторії залежностей немає, тож ставиться
на вимогу; без нього тест чесно пропускається, а в CI — падає):

```bash
npm install --no-save playwright && npx playwright install chromium
node tests/render-check.js
# якщо Chromium уже є в системі: ARM_CHROMIUM=/шлях/до/chrome node tests/render-check.js
```

## Технічні нотатки

- React підключено локально (`vendor/`), тож додаток працює офлайн.
- Шрифт Manrope підвантажується з Google Fonts; офлайн застосовується системний.
- Дані нікуди не вивантажуються — увесь розбір і збереження на пристрої.
